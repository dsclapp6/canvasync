### I1 [high] File viewer writes stale async responses over the newer file's view; render token checked only inside the PDF path

Anchor: `canvas-sync/bridge/public/app.js:1617` (finder: ui-features)

Scenario: Files tab: click View on a large slide deck (its converted-PDF blob fetch at app.js:1599 is in flight), press Back, then click View on a different file (text/markdown/page/small PDF), which renders fully. When the older request resolves, its code writes body.innerHTML unconditionally (app.js:1617 for the preview shell; same for the text path at :1589, image at :1578-1583, Canvas page at :1570, extracted-text fallback at :1667) — clobbering the newer file's content. Its subsequent renderPdfPages call then aborts on the stale renderId BEFORE clearing the loading placeholder, and the outer code just sets aria-busy=false, so the panel permanently shows the OLD file's toolbar and an eternal 'Rendering document…' box — or the old file's full text — under the NEW file's title and 'Open original' button (FILE_VIEW points at the new file).

Detail: renderFileView (app.js:1541) captures renderId = FILE_PREVIEW_RENDER at :1547, but the only consumers of that token are renderPdfPages (:1467-1489) and the render-error path (:1648). None of the four other content paths, the new preview path's own two awaits (:1599 blob, :1604 extracted text), or the catch block (:1670) re-check `renderId !== FILE_PREVIEW_RENDER` before writing into #file-body — the exact invalidation the token was added for in this release (v1.8.x file-preview slice) covers only PDF page painting, not the DOM writes around it. Every openFile call site is un-awaited (e.g. :2555 data-view-file, :1351 data-afile, :5486 chat sources), so two renders overlap freely. Fix shape: after every await in renderFileView (and at the top of the catch), bail when renderId no longer equals FILE_PREVIEW_RENDER. Violates the no-dead-states invariant: the stuck 'Rendering document…' state has no error, no fix named, and shows another file's content under the current title.

Fix direction (skeptic-verified): Add a staleness bail after every await in renderFileView and at the top of its catch: e.g. `const stale = () => renderId !== FILE_PREVIEW_RENDER;` and `if (stale()) return;` immediately after each awaited fetch/blob/text (after :1567's apiJson, :1577's blob, :1588's text, :1599's blob, :1604's extracted text, :1665's text) and as the first line of the catch (:1670), before any $('file-body')/$('file-sub')/$('file-open') write. Also have renderPdfPages clear or mark its host when it bails on a stale token only if desired — the outer guards make that unnecessary once no stale caller can have painted the shell.

Fix direction (skeptic-verified): Either exempt completed rows from the AI-origin filter (Show completed is an explicit request to see finished work, and spec 2.5 calls it the one resurrection control — e.g. in renderCalendarOps let ops tagged `_completed` bypass the isAiItemVisible stage at app.js:4753), or compute the Show-completed count/label in syncCalControls from the post-AI-filter done rows and, when the AI toggle is what zeroed it, say so on the control itself. Add a cal-plan/app-level test covering a reason:'done', origin:'syllabus' dropped record with CAL_SHOW_AI_ADDED=false and CAL_SHOW_DONE=true, and record the chosen behavior as a row under CALENDAR-SPEC 2.5/§6.16-6.21.
